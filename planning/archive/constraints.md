# 핵심 제약과 설계 원칙 (이전 기획)

## C-001: 방장 단독 설치와 순정 클라이언트 호환

### 요구사항

- RepoHell은 방장에게만 설치되어 있어도 동작해야 한다.
- 참여자는 BepInEx, RepoHell 또는 별도 의존성을 설치하지 않아도 된다.
- 순정 참여자는 모드의 핵심 효과를 실제로 보고, 듣고, 상호작용할 수 있어야 한다.
- 참여자에게 오류, 연결 해제, 진행 불가, 지속적인 상태 불일치를 유발하면 안 된다.
- “방장 화면에서만 보인다” 또는 “순정 참여자는 효과를 알 수 없다”는 정상 경험으로 인정하지 않는다.

### 의미

RepoHell은 기본적으로 **호스트 권한형(server-side/host-only) 모드**로 설계한다. 방장이 게임의 권위 있는 상태를 변경하고, 순정 게임이 원래 제공하는 Photon 동기화와 RPC를 통해 그 결과가 참여자에게 전달되어야 한다.

순정 참여자는 RepoHell 코드를 실행하지 않으므로 다음 작업을 수행할 수 없다.

- RepoHell 전용 네트워크 메시지 해석
- RepoHell 전용 UI 또는 입력 처리
- 새 C# 컴포넌트 실행
- 게임에 없는 프리팹, 에셋 또는 타입 로드
- 참여자 로컬에서만 계산되는 규칙 변경

따라서 핵심 기능이 위 작업 중 하나를 요구한다면 C-001을 만족하지 못한다.

## 설계 원칙

### 1. 호스트가 유일한 결정권자다

- 게임 상태를 바꾸는 로직은 호스트 여부를 확인한 뒤 실행한다.
- 랜덤 결과, 스폰 선택, 보상, 적 AI와 진행 상태는 호스트에서 한 번만 결정한다.
- 참여자에게 동일한 로직을 다시 계산하도록 요구하지 않는다.
- 모드를 설치한 참여자가 순정 방에 접속한 경우 RepoHell의 게임 상태 변경 로직은 비활성화한다.

### 2. 순정 네트워크 경로를 재사용한다

- 가능하면 게임이 이미 동기화하는 필드, 오브젝트, RPC와 이벤트를 사용한다.
- 새 네트워크 프로토콜보다 기존 게임 메서드를 호스트에서 호출하는 방식을 우선한다.
- RepoHell 전용 이벤트는 로깅이나 모드 설치자 간 부가 기능에는 사용할 수 있지만, 순정 참여자의 핵심 경험이 이를 필요로 해서는 안 된다.
- 패치 대상은 “결과를 만드는 호스트 측 지점”이어야 하며, 참여자의 표시 코드 패치에 의존하면 안 된다.

### 3. 순정 게임에 존재하는 콘텐츠만 사용한다

- 순정 클라이언트가 이미 가진 프리팹, 애니메이션, 오디오, 아이템과 UI 표현을 조합한다.
- 신규 아이템, 적, 맵, 모델, 사운드 또는 커스텀 UI가 핵심인 기능은 기본 범위에서 제외한다.
- 새 콘텐츠처럼 보이는 기능이 필요하면 순정 자산의 조합만으로 동일한 경험을 만들 수 있는지 먼저 검토한다.

### 4. 로컬 시뮬레이션 의존 기능을 피한다

플레이어 체력 표시, 입력, 카메라, HUD, 일부 물리·무게·내구도처럼 각 참여자 로컬에서 계산하거나 표시하는 기능은 호스트 패치만으로 일관성을 보장하기 어렵다. 이런 기능은 실제 네트워크 소유권과 동기화 경로가 확인되기 전까지 채택하지 않는다.

### 5. 실패 시 순정 동작으로 복구한다

- 패치가 적용되지 않거나 게임 버전이 바뀌면 가능한 경우 해당 기능만 비활성화한다.
- 예외가 발생해도 원본 게임 호출과 진행을 막지 않는 방향을 기본으로 한다.
- 레벨 전환, 로비 재생성, 중도 참가 시 모드가 만든 임시 상태를 다시 계산하거나 제거한다.
- 저장 데이터 형식은 순정 저장과 호환되어야 하며, 모드를 제거해도 세이브가 손상되지 않아야 한다.

## 기능 적합성 빠른 판정

다음 질문에 모두 `예`라고 답할 수 있어야 한다.

1. 기능의 결정 로직을 방장에서만 실행할 수 있는가?
2. 결과를 순정 게임의 기존 상태/RPC로 전달할 수 있는가?
3. 순정 참여자가 별도 코드 없이 결과를 인식하고 상호작용할 수 있는가?
4. 커스텀 에셋이나 새로운 네트워크 타입이 없어도 핵심 경험이 유지되는가?
5. 중도 참가자가 현재 상태를 순정 동기화만으로 받을 수 있는가?
6. 기능이 실패하거나 모드가 제거되어도 진행과 저장이 유지되는가?

하나라도 `아니오`이거나 확인되지 않았다면 구현 전 기술 실험이 필요하다. 실험으로도 해결되지 않으면 해당 기능은 기각한다.

## 범위 예시

### 적합 가능성이 높은 기능

- 호스트가 결정하는 스폰 수량·선택·배치 변경
- 기존 적 AI의 호스트 측 의사결정 변경
- 기존 상점 가격, 보상, 목표 수치 등 동기화되는 규칙 변경
- 기존 오브젝트와 효과를 이용한 이벤트
- 호스트에서 검증하는 상호작용 권한 또는 진행 조건 변경

### 부적합 가능성이 높은 기능

- 참여자에게 새 HUD나 메뉴를 표시하는 기능
- 참여자의 새 키 입력이나 로컬 카메라 처리가 필요한 기능
- 신규 프리팹, 아이템, 적, 맵 또는 커스텀 오디오 배포
- RepoHell 전용 RPC를 받아야만 보이거나 작동하는 기능
- 참여자 로컬 물리나 스탯 계산을 직접 패치해야 하는 기능

이 목록은 절대적인 판정표가 아니다. 실제 채택 여부는 게임 코드와 멀티플레이 실험으로 확인한다.

## 의존성 정책

- Thunderstore의 설치 의존성은 방장에게만 적용되는 BepInExPack을 기본으로 한다.
- 다른 모드 라이브러리를 추가할 때도 참여자 설치가 필요해지는지 먼저 검증한다.
- REPOLib 등의 커스텀 네트워크 이벤트를 핵심 동기화 수단으로 사용하지 않는다. 순정 참여자는 해당 핸들러를 갖고 있지 않기 때문이다.
- 가능한 기능은 게임 자체 API와 Harmony 패치만으로 구현한다.

## 알려진 기술적 배경

R.E.P.O.는 Photon 기반이며 많은 게임 상태가 호스트(Master Client) 중심으로 처리된다. 실제 호스트 전용 모드들도 호스트가 스폰, 상점 또는 상호작용 결과를 결정하고 순정 동기화를 재사용하는 방식으로 동작한다. 반대로 체력, 물리, UI처럼 클라이언트별 로컬 처리가 필요한 변경은 모든 참여자의 설치가 요구될 수 있다.
